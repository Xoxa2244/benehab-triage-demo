# План переработки: облегчённая версия (только цветовой тест)

## 1) Цель
Сделать отдельную облегчённую ветку продукта в папке `lite-color-test`, где остаётся только функциональность цветового теста: управление проектами, понятиями, метриками, прохождение опроса, хранение и просмотр результатов.

## 1.1) Подтверждённые решения
- Lite — это **полностью отдельное приложение**.
- Значения в матрицах метрик: от `0.0` до `1.0` с шагом `0.1` (dropdown).
- Цветовая палитра редактируемая.
- Synthetic users хранятся постоянно (в БД).
- Lite стартует с нуля, без миграции legacy-данных.

## 2) Что уже есть в коде (база для переиспользования)
- Frontend-опрос: `pages/profiling/values.js` (2 этапа, но UX не соответствует новым требованиям).
- Backend цветового теста: `backend/routes/color_test_router.py` (`/color-tests`, `/color-tests/inputs`, `/color-tests/concepts`).
- Метрики: `backend/routes/metric_router.py` + прокси `pages/api/metrics/*`.
- Редактирование понятий/метрик и матриц уже частично есть в `pages/staff-console.js` (можно использовать как прототип).

## 3) Предлагаемая структура lite-версии

```text
lite-color-test/
  REWORK_PLAN.md
  README.md
  frontend/                # отдельное standalone web-приложение
  backend/                 # отдельный standalone backend для lite
  docs/
```

Принцип: не ломаем существующие экраны в основном продукте; Lite разворачивается и запускается как изолированное приложение со своим frontend/backend-контуром.

## 4) Целевая модель данных

### 4.1 Project
- `id`, `name`, `description`, `status` (`draft|active|archived`), `created_at`, `updated_at`.
- `concepts`: упорядоченный список объектов (`id`, `label`, `position`, `is_active`).
- `metric_ids`: упорядоченный список метрик, привязанных к проекту.
- `palette`: упорядоченный список цветов проекта (`id`, `label`, `hex`, `position`, `is_active`).

### 4.2 Metric
- `id`, `project_id`, `name`, `position`, `is_active`.
- `similarity_same_weights`, `similarity_diff_weights`, `attractiveness_rank_weights`.
- Матрицы зависят от текущего состава и порядка понятий проекта.
- Каждая ячейка матриц хранит значения из дискретного набора: `0.0, 0.1, 0.2, ... , 1.0`.

### 4.3 SyntheticUser
- `id`, `display_name`, `kind` (`synthetic`), `note`, timestamps.
- Хранится постоянно в БД, участвует в фильтрах и истории прохождений.

### 4.4 SurveyRun
- `id`, `project_id`, `user_id`, `user_name_snapshot`, `started_at`, `completed_at`.
- `concept_color_choices` (этап 1), `color_rank_order` (этап 2), `calculated_metrics`.

## 5) API (lite-контур)

Префикс: `/api/*` внутри отдельного Lite-backend.

- `GET/POST /projects`
- `GET/PUT/DELETE /projects/{projectId}`
- `GET/PUT /projects/{projectId}/concepts` (полный ordered payload)
- `GET/PUT /projects/{projectId}/palette` (редактируемая палитра и порядок цветов)
- `GET/PUT /projects/{projectId}/metrics-order`
- `GET/POST/PUT/DELETE /projects/{projectId}/metrics`
- `POST /projects/{projectId}/survey-runs`
- `GET /survey-runs` (фильтры: project, user, date)
- `GET /results/users` (агрегация итогов по пользователю)
- `GET/POST /synthetic-users`

## 6) UI Lite (обязательные экраны)

### 6.1 Projects
- Список проектов + создание/дублирование/архивация.
- Проекты полностью независимы по понятиям, метрикам и результатам.

### 6.2 Concepts (список, не теги)
- Табличный/линейный список.
- Drag & drop reorder.
- Явный статус сохранения: `Сохранено` / `Есть несохранённые изменения` / `Ошибка сохранения`.

### 6.3 Metrics
- Редактируемые метрики.
- Отдельный reorder списка метрик (drag & drop).
- Редактирование матриц через dropdown в каждой ячейке (вместо свободного numeric input).
- Варианты dropdown: `0.0 ... 1.0` с шагом `0.1`.

### 6.4 Survey Stage 1 (понятие → цвет)
- На экране только одно понятие и выбор одного цвета.
- Кнопки `Назад/Далее`, прогресс, блокировка перехода без выбора.
- Без текущей механики «несколько понятий и пять+ цветов на одном экране».

### 6.5 Survey Stage 2 (ранжирование цветов)
- Один экран без скролла.
- Слева/сверху: репозиторий доступных цветов (из палитры выбранного проекта).
- Справа/снизу: линейка `самый приятный → самый неприятный`.
- Drag & drop из репозитория на линейку и обратно (без “залипания”).

### 6.6 Results
- Таблица `Результаты пользователя`: пользователь, проект, итоговые значения метрик.
- Реестр прохождений: кто/когда/какой проект/какие метрики/показатели.
- Фильтры и сортировка по проекту/дате/пользователю.

### 6.7 Synthetic users
- Быстрое создание тестовых сущностей.
- Возможность многократно проходить опрос от разных synthetic users.

## 7) Этапы внедрения

1. Создать каркас отдельного приложения `lite-color-test` (standalone frontend + standalone backend).
2. Добавить backend-модели `Project`, `SurveyRun`, `SyntheticUser`; реализовать проектные `concepts` и `palette`.
3. Реализовать API проектов/понятий/палитры/метрик с упорядочиванием.
4. Сделать lite-admin UI (Projects, Concepts, Metrics) с состояниями сохранения.
5. Реализовать новый Survey UX (Stage 1 и Stage 2 по требованиям).
6. Реализовать Results UI + API агрегаций.
7. Добавить smoke/e2e тесты ключевых сценариев.

## 8) Критерии приёмки
- В Lite-интерфейсе отсутствуют лишние вкладки/сущности вне цветового теста.
- Понятия и метрики редактируются и reorder работают стабильно.
- Палитра проекта редактируется и участвует в прохождении опроса.
- Пользователь всегда видит состояние сохранения изменений.
- Проекты изолированы: изменения проекта A не влияют на B.
- Survey Stage 1 и Stage 2 соответствуют UX-требованиям 1-в-1.
- Таблицы результатов и реестр прохождений доступны и фильтруются.
- Поддержаны многократные прогоны через synthetic users.

## 9) Риски и технические замечания
- Сейчас концепты глобальные (singleton `ConceptDocument`), это конфликтует с проектной моделью.
- Метрики сейчас глобальные (`/api/metrics`), нужно проектное разделение.
- Часть текущего UI опирается на localStorage; для реестра прохождений нужен backend-first источник истины.
- Миграция legacy-данных не требуется: Lite запускается с чистой схемой и нулевым baseline.
